# Project: Go Statusengine Worker

A highly performant, concurrent Go-based event pipeline. It consumes bulk JSON messages from queues (Gearman/RabbitMQ), flushes them via throttled bulk-inserts into MySQL, extracts metrics for Graphite, and broadcasts events selectively via non-blocking WebSockets.

## Tech Stack & Core Packages
- **Language:** Go (Latest stable, strict concurrency compliance)
- **Database:** MySQL 8.0+ (Driver: `go-sql-driver/mysql`)
- **WebSockets:** `gorilla/websocket` or `melody`
- **Legacy Reference:** https://github.com/statusengine/worker (Reference for domain logic, event types, and processing rules)

## System Context & Specs
- **Database Schema:** Read `/.claude/specs/mysql_schema.sql`
- **Queue Payload Examples:** Read JSON dumps in `/.claude/specs/` (Note: Each queue delivers a specific type, but payloads arrive as a JSON bulk array).
- **Queue Payload Bulk Exceptions:** The Queues `statusngin_acknowledgements`, `statusngin_contactnotificationmethod.json`, `statusngin_core_restart.json` and `statusngin_downtimes` do not use bulk payloads.
- **WebSocket/Metrics API Reference:** `docs/openapi.yaml` (OpenAPI 3.1, viewable via `docs/index.html` with Scalar) - the `/ws` message envelope and a real captured example for every event topic, including the `statusngin_downtimes` `type`/`attr` lifecycle table.

## Implementation Status
Every queue is wired end-to-end in `internal/queue/registry.go`'s `NewRouter` - decoded, persisted to MySQL where applicable (rule 3), and broadcast (rule 4):

- **Done** — Host/Service Status, Host/Service Checks, Perfdata (rule 5 MySQL/Graphite routing)
- **Done** — Notifications (`statusngin_notifications`, `statusngin_contactnotificationmethod`)
- **Done** — Acknowledgements (`statusngin_acknowledgements`)
- **Done** — State Changes (`statusngin_statechanges`)
- **Done** — Core Restarts (`statusngin_core_restart`)
- **Done** — Downtimes (`statusngin_downtimes`) - full ADD/LOAD/START/STOP/DELETE lifecycle across the `scheduleddowntimes`/`downtimehistory` table pairs; doesn't use the BulkInserter abstraction (see `.claude/specs/downtime_ablauf.txt` for the processing matrix and why)
- **Done** — Prometheus metrics exporter (`internal/metrics`, served on its own port, default `:9105/metrics`). **Every labeled series is pre-created at zero on startup**, so a fresh worker exports all 12 `queue_name`, 18 `table` (14 of them also on `db_flushes_total`) and 4 `component` series instead of growing them as traffic arrives - otherwise a panel reads "No data" exactly while everything is healthy, and an alert on it never evaluates. `metrics.InitQueue`/`InitTable`/`InitFlushes` do that; the calls sit where the label values are actually known (`db.NewBulkInserter` for its own table, `queue.NewRouter` for the router's keys and the four downtime tables that bypass BulkInserter, the metrics package's own `init` for the components), so a new inserter or queue is covered without a second list to keep in sync. `InitFlushes` is deliberately *not* called for the four downtime tables: they write one row per statement without batching, and a permanent 0 denominator under a climbing `db_events_written_total` would make the rows-per-flush ratio read `+Inf` rather than "not applicable". Only safe because all these label sets are small and fixed - never do this for an open-ended label like a client id or hostname.
- **Done** — Data retention (`internal/cleanup` + `cmd/db_cleanup`) - a separate one-shot binary for cron/systemd timers, not part of the worker process

## Core Architecture Rules

### 1. Queue Abstraction (Pluggable Ingestion)
- Decouple queue backends using a Go `Consumer` interface (e.g., `Start()`, `Stop()`).
- Support both **Gearman** and **RabbitMQ** as swappable drivers. Gearman is the production backend.
- The Gearman client is a patched fork, `github.com/nook24/gearman-go`, pulled in via a `replace` directive in go.mod (pinned to the published release `v1.1.1`, never a local directory path - that would build only on one machine). It carries three fixes. Two are data races: upstream's `Worker.Close()` closed its job channel while the agent goroutines were still sending on it, and `worker.running` was written under the worker mutex but read from `exec` without it. Both are fixed (agent WaitGroup awaited before the close; `running` is an `atomic.Bool`), which is what lets the full suite run under `-race` without skipping anything. The third is why a restart no longer duplicates work: `Close()` used to clear `running` and drop the connections *before* waiting, and `exec` writes a job's WORK_COMPLETE only while `running` is true - so every handler still running finished its work and then silently skipped its acknowledgement, and the server re-queued exactly those jobs. `Close()` now drains in-flight jobs first, bounded by `DrainTimeout` (30s) so a stuck handler cannot turn a shutdown into a hang. See rule 6.
- **Payloads are UTF-8-normalized before decoding** (`repairUTF8` in `internal/queue/utf8.go`, applied once in `observeHandler`). Windows plugins commonly emit umlauts as CP1252 and Naemon passes that straight into the JSON, where only UTF-8 is legal. Go does not reject it the way PHP's `json_decode` does - `encoding/json` substitutes U+FFFD instead, so the corruption would be silent and reach MySQL as valid UTF-8. Only bytes that are provably invalid are reinterpreted (per byte, not per document, so a bulk payload mixing a UTF-8 host with a Windows one keeps both intact - the legacy `src/JSONUTF8.php` mangles that case). `statusengine_queue_payloads_repaired_total` shows when it happens; a non-zero value means some host should be fixed at the source.
- **One Gearman connection per queue, each registering exactly that one function.** Not one connection carrying all twelve, which is what this was until a load test found the problem: with a backlog of 10,000 `statusngin_servicestatus` jobs, that queue was drained to the last job before any other queue was looked at. The cause is in this process, not in gearmand. The library's `Work()` is a single goroutine ranging over a single channel fed by every agent, and `handleInPack` does `worker.limit <- true` from inside it (`worker.go:198`); that send blocks once the concurrency cap is reached, and while it blocks the loop reads nothing further from any agent, for any function. Since a Handler blocks in `Enqueue` for as long as MySQL needs (rule 3), a status backlog parks every slot on MySQL's write rate - so notifications, downtimes and core restarts are not merely slow, they are never dispatched. That is a liveness problem, not a throughput one. Splitting the connections gives each queue its own `Work` loop and its own budget; `TestOneQueueCannotConsumeTheWholeJobBudget` holds every slot with one queue and insists another is still served. Measured end-to-end against a 2,000-job backlog: before, a second queue's 200 jobs sat at **0 for the full ~6s** until the backlog cleared; after, they completed within 2s while the backlog was ~30% done. This is what the legacy PHP worker gets from forking one client per queue, and what the RabbitMQ consumer here already did with one channel and one `consumeLoop` per queue - the two backends were behaving differently, and that was never intentional.
- **`Stop` must close those connections in parallel** (`closeWorkers`). `Close` drains in-flight jobs before dropping the connection, bounded by `DrainTimeout` (30s); closing twelve one after another would make the worst case six minutes, long past the point a service manager escalates to SIGKILL - which would lose exactly the buffered rows the graceful shutdown exists to flush. `TestCloseWorkersDrainsInParallel` measures it against real stuck handlers, because that is the only state in which `Close` actually spends its timeout: 0.30s parallel vs 1.80s sequential at six workers.
- **An empty Router is rejected by `Start`.** The connections are opened inside the per-queue loop, so with no queues `Start` would return success having connected to nothing and consumed nothing forever. Before the split, a single connection was opened up front and that case at least failed on an unreachable server.
- **gearmand 2.0.0** (released 2026-07-22, previous release 1.1.22) changes **no wire protocol or packet format**, so `mikespook/gearman-go` stays compatible and needs no adaptation. Its three breaking changes are scheduling behaviour: round-robin job assignment is now the default and can no longer be disabled, job priority is now global rather than per function, and the client-side task list is FIFO instead of LIFO (that one affects publishers, not this worker). Round-robin changes only *which* pending job the server offers, and the Go client just sends `GRAB_JOB_UNIQ` and takes what it gets - so on the old single-connection shape it would have spread the shared budget around and softened the starvation above without removing it, since the coupling was in-process. With one connection per queue it is genuinely neutral, and correctness no longer depends on a server flag this worker can neither verify nor enforce (`-R` is off by default on gearmand 1.x).

### 2. High-Throughput Processing & Concurrency
- **Non-Blocking Architecture:** Ingestion, Database persistence, and WebSocket broadcasting **must** run on separate Goroutines decoupled by channels. WebSockets must never slow down DB ingestion.
- **Worker Pool:** Use buffered channels and bounded worker pools to process decoded queue data concurrently.
- **The two status queues discard events older than `status_max_age` (default 5m) before doing any work with them** - `NewStaleDroppingHandler` in `internal/queue/router.go`, wired up for `statusngin_hoststatus` and `statusngin_servicestatus` only. Those two carry a full *snapshot* of an object's current state, re-sent every check interval and upserted into a single-row-per-object table, so a snapshot from ten minutes ago has no reader left: MySQL holds a newer one already. While the worker is down they accumulate one job per check interval per object, and draining that backlog costs exactly the MySQL time the live traffic then waits for. **Never extend this to another queue.** Every other queue carries history - a check result, a state change, a notification - where each event is a distinct row nothing will ever supply again, so dropping on age is straightforward data loss; `TestOnlyStatusQueuesDiscardOnAge` fails if a third queue ever gains a discard series. The comparison is between the *core's* clock and the worker's, which makes the failure mode silent: hosts more than `status_max_age` apart stop writing these two tables entirely, with nothing in the log. `statusengine_queue_events_discarded_stale_total` is the only signal, which is why it is pre-created at zero for exactly those two queues and why `0` (process everything) is a supported setting.
- **Backpressure belongs at the broker, not in the process.** A Handler is not a cheap channel write: it decodes the payload and calls `Enqueue` per item, which blocks once that BulkInserter's channel is full (`mysql_batch_size` deep, 100 by default), so its duration is governed by MySQL. Both consumers are therefore capped, and **both caps are per queue** - `-gearman-max-concurrent-jobs-per-queue` (default 8; the library otherwise dispatches every job on an unbounded goroutine and never waits) and `-rabbitmq-prefetch` (default 100; AMQP otherwise delivers as fast as it can). Per queue rather than shared, because a shared budget is one a backlogged queue takes all of - see rule 1. The process-wide worst case is therefore the cap times the number of queues; an idle queue costs nothing, since a cap only binds when there is traffic to bind. The Gearman flag was renamed rather than redefined in place: the old `gearman_max_concurrent_jobs` key and its environment variable are **rejected with a fatal error** (`rejectRetiredConcurrencyKey` in `cmd/app/main.go`), because carrying an existing 64 forward would silently mean 768 concurrent handlers, which is the unbounded-memory situation the cap exists to prevent, and there is no automatic mapping that is right - 64 shared and 64 per queue are different intentions. Surplus then waits at the broker, where it survives a worker restart and is visible via `gearadmin --status` or the RabbitMQ console. Watch `statusengine_queue_jobs_in_flight{queue_name=…}` (a queue pinned at the cap = that queue is falling behind; labeled per queue precisely because an unlabeled total cannot tell one saturated queue from twelve busy ones), `statusengine_queue_handler_duration_seconds` and `statusengine_db_batch_size_at_flush` (constant at `mysql_batch_size` = batch- rather than ticker-triggered, i.e. saturated - its buckets span the whole configurable range for exactly this reason). Adding a second worker process would make a backlog worse, not better: the bottleneck is behind the intake.
- **Nothing on the hot path logs at Info - the Info level carries lifecycle events and 30-second summaries, and nothing else.** Under systemd the log is the journal, so a line per unit of work is a disk-space problem rather than a cosmetic one: measured over a 76-second run writing ~1.96M rows across two tables, the per-flush lines alone were 19,616 entries, about **145 MB/hour**, against 20 lines (0.13 MB/hour) now. `db: bulk insert flushed`, `graphite: metrics flushed` and the per-row `queue: downtime write` are therefore **Debug**, and `logStats` in `internal/db` and `internal/graphite` replaces them with one `write stats` line per 30 seconds per table - the same interval the consumer and the Hub already used, so a log read at Info has one rhythm rather than four. Two properties are load-bearing and each has a test that fails without it (`internal/db/logvolume_test.go`, `internal/graphite/logvolume_test.go`): the detail must still be **there** at Debug, since "quieter" quietly becoming "gone" is the obvious way to regress this; and a summary is **skipped entirely when nothing was written**, because there are fourteen inserters, most tables are idle on most installations, and perfdata routes to MySQL only by default - an unconditional line would mean 30 entries a minute reporting that nothing happened, which is the same problem in slower motion. A table that stops appearing has stopped writing; that absence is the signal, with `db_events_written_total` as the precise version. `Run` emits one final summary on shutdown so a shutdown landing mid-interval still reports what it wrote. Errors are exempt from all of this - a dropped batch, an unreachable MySQL, a failed Graphite write are logged every single time, never aggregated.

### 3. Throttled Bulk-Inserts (MySQL)
- **Do not add `SET NAMES` or a `charset=` DSN parameter.** The legacy PHP worker issues `SET NAMES utf8mb4` after connecting because PDO/mysqli inherit the server default (historically latin1). `go-sql-driver/mysql` does not need it: it writes `utf8mb4_general_ci` into the handshake packet itself (`defaultCollationID`), so the connection is utf8mb4 before the first query, and naming a charset in the DSN only adds a round-trip per new connection. `logConnectionCharset` in `cmd/app/main.go` logs the negotiated charset once at startup and warns if it is not utf8mb4. Setting `collation=` to match the columns exactly (`utf8mb4_0900_ai_ci` here) is also deliberately avoided: that collation only exists on MySQL 8.0, so it would cost portability without fixing anything - stored data and comparisons use the column collation regardless.
- **Retention is a separate binary, not part of the worker** (`cmd/db_cleanup`, logic in `internal/cleanup`). It deletes rows older than a per-table number of days and exits, so it belongs in cron or a systemd timer. It reads the *same* YAML file as the worker - which works because both decode it with a plain `yaml.Unmarshal` into their own struct, so each ignores the other's keys - and uses the legacy PHP worker's config key names (`age_hostchecks`, `age_host_statehistory`, `age_host_downtimes` for the *downtimehistory* table, ...) so an existing `config.yml` carries over value for value, including its `0` = disabled convention. That convention is why the age settings are `*int` in `fileConfig` and need `resolveOptionalInt` rather than `resolveInt`: the latter reads a file value of `0` as "key absent" (correct for the worker's counts, where 0 is never meaningful), which would silently delete at the built-in default instead of switching the table off. Deletes are batched (`DELETE ... LIMIT`, default 5000) so each batch is its own short transaction rather than one statement holding locks and inflating the binlog for minutes. Nine of the fourteen tables are `PARTITION BY RANGE (<column> DIV 86400)`; the DELETE benefits from partition pruning automatically, and `DROP PARTITION` is deliberately *not* used - the partitions are maintained by another component, and the cutoff would have to snap to week boundaries.
- Implement a **Ticker- & Batch-driven Buffer** for MySQL inserts.
- Messages must be collected and executed as a single Bulk-Insert query as soon as **EITHER** of these conditions is met:
  - The buffer reaches **`mysql_batch_size` entries** (default 100, maximum 700; `graphite_batch_size` is the Graphite counterpart, default 100, maximum 1000).
  - The oldest item in the buffer reaches **250ms** (`time.Ticker`).
- **The 700-row ceiling on `mysql_batch_size` is arithmetic, not taste, and the number that has to fit is ~2x the batch size.** Every flush goes out as a server-side prepared statement - `interpolateParams` is off by default, so `mysqlConn.Exec` returns `driver.ErrSkip` for a non-empty argument list and `database/sql` falls back to Prepare/Exec/Close - and a prepared statement is limited to **65535 placeholders**. The binding case is not a normal flush but the drain: `drainPending` deliberately tops the buffer up past the batch size from `b.in`, so it reaches `2n-1` rows, and `flushBuffer` turns all of it into **one** statement. That happens on every shutdown and every core restart (`WithPaused`) under load, i.e. routinely. At n=700 the widest table (`statusengine_servicestatus`, 43 columns) needs 1399 x 43 = 60,157 placeholders, leaving room for three more columns; at n=1000 it would need 85,957 and fail with `Error 1390`, which is deterministic and therefore **not** retried by `execWithRetry` - so both status tables would stop being written with nothing but one log line per flush. `db.NewBulkInserter` panics at construction rather than allowing that, and `TestBatchSizeStaysUnderPlaceholderLimit` does the arithmetic itself over all 14 tables at the ceiling (a test that only asserted "no panic" would pass with a wrong guard). Chunking `flushBuffer` would permit a higher ceiling and was deliberately not done: it touches the one function with a measured data-loss history (rule 6) to buy throughput that is already past the flat part of the curve. `graphite_batch_size` allows 1000 because Carbon's plaintext protocol has no such limit - that ceiling is only about how many metrics one failed write drops. The batch size actually in effect is observable **without histogram support**: `rate(db_events_written_total[1m]) / rate(db_flushes_total[1m])` is the average rows per statement, per table, from two plain counters - `db_batch_size_at_flush` carries the same information but is a histogram and has no `table` label, so it can be neither broken down nor read by a system that ingests only counters.
- **An unreachable MySQL blocks the pipeline instead of draining it into nowhere.** `execWithRetry` retries a connection failure with a capped backoff (100ms doubling to 5s) for as long as its context allows - in practice until the server is back or the worker is shut down. While it waits, `Run`'s goroutine is blocked, so `Enqueue` blocks, so the handlers block, so the consumer's concurrency cap fills and the surplus stays at the broker (rule 2). This is not optional politeness: dropping instead was measured at **29,400 of 150,000 events lost for a five-second outage** - a job is acknowledged the moment `Enqueue` returns, so unlike the redelivery case there is nothing to fall back on. Verified with a TCP proxy in front of MySQL, killed mid-drain: 150,000 of 150,000, zero dropped batches, `queued=1457 running=64` at gearmand during the outage. A permanently broken MySQL therefore stalls the worker and grows a visible, recoverable backlog rather than opening a silent hole - that is the intended trade. `statusengine_db_available` is the gauge to alert on. Note also what `isConnectionError` does *not* check: MySQL 2006 ("server has gone away") and 2013 are libmysqlclient client-side numbers that `go-sql-driver` never produces - it returns `driver.ErrBadConn`, `mysql.ErrInvalidConn` or a plain `net.Error` instead. And `database/sql` retries only `driver.ErrBadConn`, only 3 times, and the driver only produces it when it can prove nothing was written - which is why the server-restart case needs handling here at all. The one accepted gap: a connection lost *mid*-statement leaves it unknown whether MySQL applied it, so the retry can duplicate a row in `statusengine_logentries` and `statusengine_perfdata` - the same two tables, the same reason (no colliding key) and the same reasoning as under rule 6.
- **A failed flush drops its batch - with exactly two exceptions, retried up to three times** (`execWithRetry` in `internal/db/db.go`): MySQL error 1205 (lock wait timeout) and 1213 (deadlock). Those two roll back only the statement and are caused by another transaction's timing rather than by this statement's content, so the identical statement usually succeeds on the next attempt; dropping the batch instead would lose up to 100 events for a condition that clears in milliseconds. Every other error is deterministic - a truncated value or a NOT NULL violation fails the same way three times, and retrying it only slows the shutdown and triplicates the log line. The realistic source of contention is `cmd/db_cleanup` deleting from a table the worker is writing to; `statusengine_db_batch_retries_total` is what makes that visible. Note that this is only safe **because** the writes are idempotent (rule 6) - retrying a plain INSERT that was rolled back mid-statement is a different and much worse proposition. Backoff is 50ms then 200ms, deliberately short and not configurable, since `Shutdown` flushes under a 5s context.

### 4. WebSocket Pub/Sub Broadcaster
- Implement a central WebSocket `Hub` using a publish/subscribe pattern.
- Connected clients can subscribe to specific event types (e.g., only `statusngin_hoststatus`).
- **One frame per job, not per event: `payload` is always a JSON array.** The batching boundary is not invented for the wire, it is the one the data already has - a job arrives from the broker as a bulk array, and `publishBatch` in `internal/queue/router.go` forwards it whole rather than exploding it into N frames for every stage downstream to pay N times. Per job instead of per event that is one `json.Marshal`, one Hub channel send, one dispatch map walk, one slot in each client's send buffer and one `write` syscall in `writePump`. Nothing is delayed to fill a frame, so it costs no latency - a batch is whatever the core sent. The four non-bulk queues still send an array, of one, so a client never branches on the payload's shape. `TestOneFrameCarriesTheWholeJob` is the guard: every other WebSocket assertion in the package is satisfied just as well by one frame per event, because a single-element array decodes into a single-element slice perfectly happily, so it feeds a three-event job and insists on one frame with three elements *and nothing after it*. Batching also fixed an ordering problem it made impossible to keep ignoring: the callers used to alternate `publish` and `Enqueue` per event, so an event's broadcast waited on the previous event's database write - and `Enqueue` blocks whenever MySQL is the bottleneck (rule 3). Publishing the batch before the enqueue loop is what rule 2 asks for and what the old shape quietly wasn't.
- **Both hub buffers now count frames, which is where the slack came from.** `sendBufferSize` (256) and `broadcastBufferSize` (1024) are unchanged numbers with a changed unit: 256 *jobs* rather than 256 events. That is the difference between well under a tenth of a second of slack on a busy feed - less than a single stall of a terminal or a garbage-collecting browser tab - and several seconds of it. Measured on the way in: a Python client doing `json.loads` + `json.dumps` + `print` sustains ~20,000 events/s at one frame per event and ~27,000 batched, so at 3,500/s it was never the client's parsing that dropped ~0.6% of messages; it was the terminal stalling for longer than 73 ms of buffer. Raising the constants would have bought the same slack, but only by deferring work rather than removing it. `web/ws_client.py --quiet` exists to make that distinction measurable rather than arguable - it counts instead of printing, so a run measures the pipeline and not the terminal.
- Use non-blocking channel writes (`select { case hub.broadcast <- msg: default: }`) or a dropped-message strategy to prevent slow network clients from backpressuring the pipeline.
- **All three WebSocket counters report events, never frames, and `websocket_frames_sent_total` is the denominator.** A frame is a whole job, so a dispatch loop incrementing per frame would keep working, keep passing every other test, and silently report an order of magnitude below what was delivered - while the whole point of these counters is comparison against `db_events_written_total` and the queue counts. `rate(websocket_messages_broadcasted_total[1m]) / rate(websocket_frames_sent_total[1m])` is the average events per frame from two plain counters, the same idiom as `db_events_written_total` / `db_flushes_total` and for the same reason (openITCOCKPIT ingests no histograms). `TestDispatchCountsEventsAndFrames` and `TestDroppedFrameCostsItsWholeBatch` pin both halves; note that they poll the registry rather than reading `hub.dispatched`/`client.dropped`, because those fields belong to `Run`'s goroutine and reading them from a test is a data race `-race` correctly rejects.
- **The two drop counters mean different things and are deliberately separate metrics.** `statusengine_websocket_messages_dropped_total` counts a *per-client* drop in `dispatch`: one client's send buffer was full, everyone else got the message. `statusengine_websocket_publish_dropped_total` counts a drop in `Publish`, i.e. the Hub's own 1024-deep inbound buffer overflowed because the `Run` goroutine is not keeping up - that event reached *no* client, so every connected dashboard went blind at once. The first is routinely non-zero for a single slow browser tab and is not worth alerting on; the second is. Folding them into one counter would bury the outage inside the noise. Batching changed the shape of both without changing their meaning: a single full buffer now costs a whole job's worth of events at once instead of one, so they move in coarser steps while moving far less often.
- API key authentication on `/ws` is always on (`-api-keys`/`STATUSENGINE_API_KEYS`): real clients send `Authorization: Bearer <key>` or `X-Api-Key`; the `?api_key=` query parameter is accepted too, only for browser clients that can't set headers on a WebSocket handshake (e.g. `web/ws-test-client.html`). Configuring no key does not disable auth - `resolveAPIKeys` in `cmd/app/main.go` generates a random one per run and logs it as a warning, so an unconfigured worker is never an open event stream. The listener binds to `127.0.0.1:8080` by default for the same reason; exposing it on the network is an explicit `-listen-addr` opt-in. See `internal/websocket/auth.go` and the `CheckOrigin` comment in `internal/websocket/client.go` for why origins are deliberately not checked.

### 5. Conditional Perfdata Routing
- Data coming from the `statusngin_service_perfdata` queue contains time-series metrics.
- Implement conditional routing via configuration toggles: write to **MySQL only**, **Graphite only**, or **both**.

### 6. Stability & Lifecycle
- Explicitly handle all errors, reconnect automatically to MySQL/Queues on connection drops.
- Implement full **Graceful Shutdown**: Catch OS signals (SIGINT/SIGTERM), stop the consumer, flush all remaining items from the 250ms DB buffers, cleanly close active WebSocket connections, and then exit.
- **Delivery is at-least-once, so every write that can collide is idempotent.** This is not a tuning detail, it is what stops a restart from losing data. A worker that is killed, OOM-killed or loses power between finishing a job and its acknowledgement reaching the broker gets that job again on restart, with its rows already in MySQL. Before this was handled, one SIGTERM under load lost **3,300 of 300,000 events (1.1%)**, measured with `cmd/losstest`: the redelivered rows collided on the PRIMARY KEY, MySQL aborted the *entire* multi-row INSERT with `Error 1062`, and `flushBuffer` dropped the batch - taking with it every fresh row that happened to share it, since batches are cut at `MaxBatchSize` regardless of job boundaries. 97 batches failed, all `rows=100`: 9,700 dropped rows = 6,400 harmless duplicates + 3,300 unrecoverable fresh events. The shutdown flush was never the cause; two uninterrupted control runs over the same path lost nothing. The fix is `newRedeliverySafeInserter` in `internal/queue/registry.go`: the ten tables with a natural PRIMARY KEY are built as upserts whose update clause names the **first column of that key**, which makes it a genuine no-op (the row only matched because that column is already equal). `redeliverySafePKColumn` is the single source of that mapping and is cross-checked against `.claude/specs/mysql_schema.sql` by `TestRedeliverySafePKColumnsMatchSchema`; a table wired up without an entry panics at construction rather than silently reverting to a plain INSERT. `INSERT IGNORE` was deliberately not used - it downgrades *every* error to a warning, including truncation and NOT NULL violations. Re-measured after the fix: 300,000 of 300,000, zero `Error 1062`.
- **The redelivery itself is gone too, as of gearman-go v1.1.1 - and that does not make the upserts redundant.** The 64 re-queued jobs were not the broker being pessimistic: the library cleared its `running` flag and dropped the connections before waiting for in-flight handlers, and it writes a job's WORK_COMPLETE only while that flag is set, so those handlers wrote their rows and then silently skipped the acknowledgement. Fixed in the fork by draining before disconnecting (see rule 1). Verified by arithmetic rather than by absence of errors: `processed` plus the jobs left at the broker now sums to exactly what was published (3,000), where it was reliably 3,064 - the 64 being the concurrency cap. The two fixes cover different halves and neither replaces the other: this one stops redelivery on an *orderly* shutdown, the upserts keep it harmless when it happens anyway - a crash, an OOM-kill, a lost acknowledgement on the network. Exactly-once is not achievable here, so the idempotent write is the load-bearing part; removing it because "redelivery no longer happens" would reintroduce the 1.1% loss on the first hard kill.
- **Two tables are knowingly not covered:** `statusengine_logentries` (AUTO_INCREMENT key) and `statusengine_perfdata` (no PRIMARY KEY at all) cannot collide, so a redelivery inserts their rows a **second time, silently** - no error, nothing in the log. Accepted rather than fixed: both are retention-managed history, where a duplicate row is less harmful than a missing event, and closing it would need a UNIQUE index - a schema change with its own migration and index cost on the two highest-volume tables in the database. `TestExcludedTablesReallyCannotCollide` fails if that ever changes.
- **Known metric side effect:** `DBEventsWrittenTotal` counts every buffered row as written, including duplicates the upsert skipped, so `db_events_written_total` briefly overstates by up to 6,400 after a restart under load.

## Development Commands
- **Initialize & Clean:** `go mod tidy`
- **Run Application:** `go run cmd/app/main.go` - every setting can also come from a YAML config file (`-config path/to/config.yaml` or `STATUSENGINE_CONFIG`, see `config.example.yaml`); precedence is CLI flag > env var > config file > built-in default
- **Test Pipeline:** `go test ./... -race -count=1`
- **Build Gearman Test Publisher:** `go build -o bin/gearman_publisher cmd/gearman_publisher/main.go` - standalone CLI that publishes synthetic test events for a single queue to a real Gearman job server (`-queue`, `-count`, `-server`), exercising the full Gearman → Router → BulkInserter path from outside the process; run with `go run cmd/gearman_publisher/main.go -queue statusngin_hoststatus -count 1000 -server localhost:4730`
- **Build RabbitMQ Test Publisher:** `go build -o bin/rabbitmq_publisher cmd/rabbitmq_publisher/main.go` - the RabbitMQ counterpart of the above (`-queue`, `-count`, `-server`, an amqp:// URL); run with `go run cmd/rabbitmq_publisher/main.go -queue statusngin_hoststatus -count 1000 -server amqp://statusengine:statusengine@127.0.0.1:5672/`
- **Build DB Cleanup:** `go build -o bin/db_cleanup cmd/db_cleanup/main.go` - one-shot retention tool for cron/systemd timers that deletes rows older than a configured number of days from the 14 history tables; same config mechanism and same YAML file as the worker (`-config`), retention per table in days via the legacy `age_*` keys (`0` disables a table), plus `-cleanup-batch-size` (5000) and `-cleanup-batch-pause` (0s); stops cleanly between batches on SIGTERM, exits non-zero only if a table failed; run with `go run ./cmd/db_cleanup -config config.example.yaml -mysql-dsn "statusengine-dev:statusengine-dev@tcp(127.0.0.1:3306)/statusengine-dev"`
- **Build Loss Test:** `go build -o losstest cmd/losstest/main.go` - proves whether the worker loses events when stopped under load, which is the one thing about CLAUDE.md rule 6 that reading the code cannot establish. Publishes `statusngin_hostchecks` events whose hostname is a unique marker (`lt-<run-id>-<seq>`, and hostname is the first column of that table's PRIMARY KEY), so a missing sequence number is proof of a lost event rather than a deduplication artifact. Three modes (`-mode publish|verify|cleanup`, shared `-run-id`); `verify` reports missing sequence numbers as compressed ranges, asks the job server how many jobs are still queued (a backlog there is not loss), and exits 1 if anything is missing. Run the worker as a **built binary, not `go run`** - `go run` spawns the worker as a child process, so SIGTERM hits the parent and never reaches the worker. This tool found the redelivery data loss described under rule 6 below, and is what proves it stays fixed; re-run it before a release.
- **Build DB Shadow Verifier:** `go build -o bin/db_verifier cmd/db_verifier/main.go` - read-only CLI that diffs the most recent rows of the legacy PHP worker's MySQL database against this Go worker's, column by column, to prove shadow-testing data parity (`-dsn-php`, `-dsn-go`, `-tables`, `-limit`, default `-tables` covers every Status/Check/History/Notification/Acknowledgement/Downtime table (excludes `statusengine_dbversion`/`statusengine_nodes`/`statusengine_perfdata`/`statusengine_tasks`/`statusengine_users`/`statusengine_logentries`, still selectable explicitly), default `-limit` 5000); run with `go run cmd/db_verifier/main.go -dsn-php "statusengine-dev:statusengine-dev@tcp(127.0.0.1:3306)/statusengine_php" -dsn-go "statusengine-dev:statusengine-dev@tcp(127.0.0.1:3306)/statusengine_go"`
